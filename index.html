Production Agent Engineering Practice 2026

Agent 記憶架構：五層記憶讓 token 成本降 90%，並讓 Agent 真正學會

原文標題：Agent Memory Architecture — 5 Layers That Cut Token Cost 90% and Make Your Agent Actually Learn。綜合 CoALA 認知架構、Mem0、Anthropic 記憶系統、Snowflake 本體論研究與 LangChain 生產工程材料。

獨立整理｜2026 年 9 月 非 Anthropic 官方、未經其背書 台灣繁體中文譯本

摘要

你的 Agent 每天早上都讀同一批 12 個檔案，得到同樣的結論，再向你收同一筆 token 費用。兩年內模型聰明了十倍，但每次工作階段結束，它還是什麼都忘。這份筆記提出能解這個問題的五層記憶架構：工作記憶（上下文視窗）、情節記憶（發生過什麼）、語意記憶（什麼為真）、程序記憶（怎麼做），以及遺忘（該刪什麼）。我們整理的證據包括：Mem0（token 減少 90%、延遲降低 91%）、Snowflake（單一本體層讓準確率提升 20%），以及多套生產系統的實務——2026 年的瓶頸是記憶，不是模型。文中附實作程式碼、樣板、決策框架與上線檢查清單。

索引詞：Agent 記憶、工作記憶、情節記憶、語意記憶、程序記憶、遺忘、知識圖譜、上下文視窗、CoALA、Mem0。

I. 問題：規模化失憶

為什麼世上最聰明的模型，還是什麼都記不住

每一次模型呼叫，都從空的上下文視窗開始。上一輪的發現、決策、修正與偏好全都不見了。昨天花 40 分鐘除錯遷移腳本的 Agent，今天根本不記得那支腳本存在。它會再讀同一批檔案、試同一套做法、撞同一批死胡同，再跟你收同一筆 token［1］。

產業把大量資源投在讓模型更聰明——更大的上下文、更好的推理、更快的推論。但沒有記憶的智慧，只是《今天暫時停止》。一位每次對話都失憶的天才同事，不算同事；他是你每天早上都得重新簡報的昂貴顧問。

CoALA 框架（Cognitive Architectures for Language Agents）提供了詞彙：工作記憶、情節記憶、語意記憶、程序記憶［2］。這些不是從心理學借來的比喻，而是工程分層——各層有不同的儲存、檢索與過期特性。生產級 Agent 需要全部五層，包含防止矛盾堆疊的遺忘引擎。

II. 第一層：工作記憶

工作記憶就是上下文視窗。它裝著系統提示、當前對話、工具結果、檢索到的文件，以及任何注入的狀態。視窗滿了之後，舊內容不是被截斷就是被壓縮。多數 Agent 停在這一層——這正是它們失憶的原因［2］。

B. 溢位問題

上下文視窗滿了，Agent 必須決定留下什麼、丟掉什麼。多數系統從頭截斷——先刪最舊的訊息。這會毀掉任務定義、早期決策，以及走到現況的推理過程。比較好的做法：在重要內容消失之前，先溢位到情節記憶。

清單 1 — 上下文溢位處理器

def handle_overflow(context, episodic_store, budget):
    if len(context.tokens) > budget * 0.85:
        # 截斷前先保存重要內容 / Save important content before truncation
        decisions = extract_decisions(context)
        facts = extract_facts(context)
        episodic_store.save(decisions, facts)
        # 壓縮上下文：保留近期內容與已存參照
        context.compact(keep_recent=budget * 0.6)
    return context

III. 第二層：情節記憶

情節記憶記錄 Agent 互動中發生過的事：嘗試過哪些任務、試過哪些做法、哪些成功、哪些失敗、為什麼。它是 Agent 的經驗日誌。沒有它，Agent 會重複犯錯、重新發明解法［2］。

A. 該存什麼

不是每樣東西都該進情節記憶。該存：任務描述與結果、工具呼叫與回傳、錯誤與排除方式、決策與理由、使用者修正與偏好。不該存：冗長推理鏈（應壓縮）、原始文件全文（用 ID 參照）、中間草稿（只留定稿與關鍵修訂點）。

清單 2 — 情節記憶紀錄

@dataclass
class Episode:

B. 檢索策略

新任務進來時，Agent 應先查情節記憶裡相似的舊任務，再開始動手。相似度可用任務描述嵌入、工具重疊或明確標籤計算。檢索到的情節會告訴 Agent：這件事很像 task-042，當時失敗是因為遷移腳本第 47 行有打字錯誤。直接跳到修正即可。單次檢索就能省下一整段除錯過程［3］。

C. 過期

沒有過期政策的情節記憶會無限膨脹。舊情節會失效——程式庫改了、API 升級了、使用者偏好變了。預設保留最近 90 天；高價值結果永久封存；例行情節 30 天後過期。讓使用者用明確釘選覆寫這套規則。

IV. 第三層：語意記憶

語意記憶存放對世界的耐久事實：「使用者偏好 TypeScript」「API 端點是 /v2/users」「正式環境資料庫在 AWS us-east-1」。這些事實不會隨工作階段結束而消失。它們是 Agent 累積的知識——從情節經驗蒸餾成可查詢的儲存［2］。

B. 本體層

Snowflake 的研究顯示：加上單一本體層——定義實體類型、關係類型與驗證規則的 schema——Agent 準確率提升 20%，工具呼叫減少 39%［4］。本體不必複雜。簡單定義即可：使用者有姓名與偏好，專案有負責人與期限，API 有端點與驗證方式。Schema 約束 Agent 存什麼、怎麼查，避免知識庫變成一堆沒結構的觀察紀錄。

清單 3 — 最小本體 schema

ontology = {
    "entity_types": ["user", "project", "api", "config"],
    "relation_types": ["prefers", "owns", "depends_on", "located_at"],
    "validation": {
        "user.prefers": {"target": "string", "expires": "90d"},
        "project.owns": {"target": "user", "required": True},
        "api.located_at": {"target": "string", "required": True},
    },
}

C. 衝突處理

當 Agent 學到使用者現在偏好 Python 而不是 TypeScript，它必須更新語意記憶，而不是再附加第二筆偏好。衝突處理讓語意記憶保持一致：偵測重複、合併相容事實、覆寫過期內容，並把真正的矛盾標給人看。沒有衝突處理，語意記憶會堆滿矛盾，Agent 行為就會前後不一。

V. 第四層：程序記憶

程序記憶存放方法。Agent 試過三種前端部署做法，其中一種成功。那個做法就變成可重用技能：有名稱、步驟、工具、前置條件與成功標準。下次再出現同樣任務，Agent 載入技能，直接做有效的那套［2］。

A. 技能結構

清單 4 — 程序記憶技能

@dataclass
class Skill:
    name: str
    trigger: str  # 何時使用此技能
    steps: list[str]
    tools_required: list[str]
    preconditions: list[str]
    success_criteria: str
    failure_modes: list[str]
    version: int
    last_used: datetime
    success_rate: float

B. 技能晉升

不是每次成功都值得變成技能。只有在這些條件成立時才晉升：任務至少每週重複、方法至少成功三次、步驟能無歧義描述、所需工具穩定可用。一次走运的成功是情節，不是技能。晉升門檻避免程序記憶塞滿脆弱、高度依賴情境的做法。

C. 技能版本

部署流程一變，舊技能就失效。像軟體一樣做版本：更新步驟、遞增版號、保留上一版以便回溯，並對當前環境重新驗證。過期技能比沒技能更糟——它會產生「很有把握的錯」。

VI. 第五層：遺忘

該刪什麼——最重要、卻幾乎沒人做的一層。

從不遺忘的 Agent 會累積矛盾。使用者從紐約搬到倫敦，Agent 還在推薦布魯克林餐廳。API 從 v1 遷到 v2，語意記憶裡兩個端點都在，Agent 還在打 v1。部署流程改了，舊技能因歷史成功率較高，Agent 仍照舊走［5］。

A. 遺忘不是缺陷

在人類認知裡，遺忘是功能。它避免無關記憶淹沒相關記憶，讓過期事實衰減以化解矛盾，並修剪不再重要的資訊以降低認知負荷。Agent 記憶系統需要同一套機制：刻意設計的遺忘引擎，負責修剪、覆寫與化解［5］。

B. 三種遺忘操作

表 IV — 遺忘操作
操作做什麼何時用

覆寫取代用新版本替換舊事實事實已變更

清單 5 — 遺忘引擎

def forget(memory, rules):
    # 讓舊情節過期
    for ep in memory.episodic:
        if ep.age > rules.episodic_ttl:
            memory.archive(ep)
    # 覆寫過期的語意事實
    for fact in memory.semantic:
        newer = memory.find_newer(fact)
        if newer:
            fact.status = "superseded"
            fact.superseded_by = newer.id
    # 標出矛盾
    conflicts = memory.find_conflicts()
    for c in conflicts:
        memory.flag_for_review(c)

實證、反模式與樣板

原文在第五層之後接續一組證據、反模式與設定樣板（原文章節編號沿用 A–H）。

A. Mem0：token 減少 90%

Mem0（GitHub 超過 5.1 萬星）在應用與 LLM 之間放一層記憶。它不再把整段對話塞進每次 API 呼叫，而是抽出相關事實存進持久層。下次查詢只注入相關事實——通常是 1,800 個 token，而不是 26,000。結果：每次查詢少 90% token，延遲低 91%。有回報指標的生產使用者，幾乎都在部署第一天就回本［3］。

B. Snowflake：本體勝過蠻力

Snowflake 的 AI 工程團隊，在內部資料平台上比較有無本體層的 Agent 表現。本體定義實體類型（資料表、欄位、使用者、查詢）、關係類型（owns、depends_on、queries）與驗證規則。加上本體後，準確率提升 20%，工具呼叫減少 39%。本體沒有新增 Agent 原本沒有的資訊，而是把既有資訊整理到能被有效找到、用到［4］。

C. Anthropic：範圍隔離的記憶

Anthropic 的 Claude 以嚴格的專案範圍隔離實作記憶。一個專案裡存的事實，對其他專案不可見。這能避免交叉污染：寫程式 Agent 的偏好不會滲進寫作 Agent 的風格。架構把記憶當第一級安全邊界，而不只是便利功能。每個記憶庫有自己的讀寫權限、過期政策與稽核軌跡［7］。

D. 前沿 Agent 的落差

SWE-bench 等基準顯示，前沿模型在需要超過 20 次工具呼叫的真實長程任務上，大約只到 62.2%。主要失敗模式不是推理，而是上下文流失。Agent 在第 3 步發現的事，到第 15 步就忘了。多步任務需要記憶；記憶需要架構，而不只是更大的上下文視窗。

F. 記憶稅

記憶不是免費的。每次檢索都加延遲，每筆事實都佔空間，每次遺忘都要運算。架構必須能自證：若記憶檢索省下的 token 超過維護成本，這套架構就划算。Mem0 的數字（token 降 90%）證明做得到，但前提是有紀律的儲存——不是全存。

H. 樣板：具備記憶意識的系統提示

樣板 2 — 帶記憶的系統提示

You have access to a persistent memory system.
Before starting any task:
1. Query episodic memory for similar past tasks
2. Load relevant semantic facts into context
3. Check if a procedural skill exists for this task type
After completing any task:
1. Save the outcome to episodic memory
2. Extract any new durable facts to semantic memory
3. If this approach worked 3+ times, propose it as a skill
Never assume you remember something from a previous session.
Always check memory. Memory is the source of truth, not your training.

A. 第 1–2 天：先做情節記憶

從最簡情節記憶開始：把每次任務結果附加到一個 JSON 檔。新任務開始前，讀最近 10 筆並把摘要注入上下文。光這樣就能避免 Agent 重蹈昨天的覆轍。實作成本是每個工作階段一次寫檔、一次讀檔。

B. 第 3–4 天：語意記憶

從情節記憶抽出耐久事實：使用者偏好、專案設定、API 端點、團隊慣例。用簡單鍵值或 SQLite 表存放。開工前把相關事實注入上下文。此後 Agent 不必每次被提醒，就記得使用者偏好 TypeScript。

C. 第 5–6 天：技能與遺忘

同一任務類型、同一做法成功三次，就把做法存成具名技能。事實衝突時保留較新者，並把舊的標成已覆寫。情節超過 30 天就封存。系統從此會學習、會記得、也會自己打掃。

D. 第 7 天：串起整條管線

把各層接起來：上下文溢位觸發情節寫入，情節模式觸發語意抽取，語意方法觸發技能建立，遺忘引擎每天跑。測試方式：做一個跨多個工作階段的任務，第 7 天還要記得第 1 天的決策。若 Agent 不必重讀原始檔就能記得，管線就通了。

VIII-B. 實作模式

各記憶層的生產級程式碼。

A. 用 JSONL 做情節記憶

最簡情節庫是 JSONL——每行一個 JSON 物件，任務結束後附加。JSONL 天生只附加，比較不怕並行寫入把檔案寫壞。每行就是清單 2 的情節紀錄。檢索時讀最近 N 筆，或依任務描述關鍵字過濾。

清單 6 — 情節儲存實作

class EpisodicStore:
    def __init__(self, path="memory/episodes.jsonl"):
        self.path = path

    def save(self, episode):
        with open(self.path, "a") as f:
            f.write(json.dumps(asdict(episode)) + "\n")

    def retrieve(self, query, top_k=5):
        episodes = [json.loads(l) for l in open(self.path)]
        scored = [
            (ep, similarity(query, ep["task_description"]))
            for ep in episodes
        ]
        scored.sort(key=lambda x: x[1], reverse=True)
        return [ep for ep, _ in scored[:top_k]]

B. 用 SQLite 做語意記憶

生產語意記憶用 SQLite，就能兼顧耐久、查詢能力與零基礎設施。Schema 定義實體類型、關係類型與事實紀錄。每筆事實有來源（哪個情節產生）、時間戳與狀態（active、superseded、flagged）。這是最小可用的知識圖譜。

清單 7 — 語意儲存 schema

CREATE TABLE facts (
    id INTEGER PRIMARY KEY,
    entity TEXT NOT NULL,
    entity_type TEXT NOT NULL,
    relation TEXT NOT NULL,
    value TEXT NOT NULL,
    source_episode TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    status TEXT DEFAULT 'active',
    superseded_by INTEGER REFERENCES facts(id)
);

C. 用 YAML 做程序記憶

技能存成 YAML，一個技能一個檔。檔案包含觸發條件、步驟、所需工具與成功標準。Agent 啟動時載入所有觸發條件，對進來的任務做比對。符合時把完整技能載入工作記憶，當成指令集。

D. 完整記憶管線

清單 9 — 具備記憶意識的 Agent 迴圈

def agent_with_memory(task, memory):
    # 1. 先看程序記憶有沒有對應技能
    skill = memory.procedural.match(task)
    if skill and skill.success_rate > 0.8:
        return execute_skill(skill, task)
    # 2. 查情節記憶中的相似舊任務
    episodes = memory.episodic.retrieve(task, top_k=3)
    # 3. 載入相關語意事實
    facts = memory.semantic.query(task.entities)
    # 4. 注入工作記憶並執行
    context = build_context(task, episodes, facts)
    result = llm.call(context)
    # 5. 把結果寫回情節記憶
    memory.episodic.save(Episode(task, result))
    # 6. 抽出新事實到語意記憶
    new_facts = extract_facts(result)
    memory.semantic.store(new_facts)
    # 7. 檢查是否該晉升技能
    if memory.episodic.count_successes(task.type) >= 3:
        memory.procedural.promote(task.type)
    return result

XI. 限制

A. 記憶不是理解

存了事實，不保證 Agent 用得對。語意條目「使用者偏好 TypeScript」幫不上忙，若 Agent 無法把偏好轉成程式碼生成決策。記憶補強模型的推理，不能取代推理。架構讓更多資訊可用，模型仍須自己推理。

B. 遺忘可能丟掉重要脈絡

過期政策太兇，會刪掉只出現一次、卻極關鍵的決策。太保守又會堆雜訊。正確平衡取決於領域：醫療 Agent 應保留情節數年；寫程式 Agent 多數情節 30 天後即可過期。讓使用者釘選永不逾期的重要情節。

C. 語意記憶需要維護

事實會變。API 會搬家。團隊會改組。偏好會演化。一月還準的語意記憶，到九月可能危險地錯。定期稽核：把存著的事實對當前現實。90 天未再確認的事實要標註。讓使用者能直接改正。

XI-B. 多 Agent 系統的記憶

多個 Agent 協作時，記憶變成協調機制。Agent A 發現一個事實，十分鐘後 Agent B 需要它。沒有共享記憶，B 得從頭再發現一次。有共享語意記憶，B 查庫就能立刻拿到。記憶系統可以取代整類 Agent 之間的通訊［6］。

B. 讀寫者問題

兩個 Agent 同時更新同一筆語意事實，其中一次寫入會蓋掉另一次。記憶系統需要並行策略：last-write-wins（簡單但會丟資料）、衝突時合併（完整但複雜），或每個實體單一寫入者（簡單且安全）。多數生產系統應預設單一寫入者：每筆事實由一個 Agent 擁有，其他 Agent 只讀不寫。

C. 記憶當共享大腦

在 SpaceXAI Playbook 架構裡，Manager Bot 維護所有任務、負責人、狀態與期限的總帳。這本總帳就是共享語意記憶。專精 Bot 讀它以了解有什麼工作，再把結果寫回去。總帳取代以對話為中心的協調：Agent 不互相傳訊，而是讀寫共享庫。系統因此能擴充，避開 Agent 兩兩通訊的 N² 問題。

XIII. 進階記憶模式

生產規模記憶系統的技法。（原文此處跳過 XII，結論仍標為第十二章。）

A. 階層式摘要

情節記憶超過數千筆後，原始檢索會變吵。階層式摘要把舊情節壓成不同時間尺度的摘要：從單筆做成日摘要，日摘要做成週摘要，週摘要做成月摘要。Agent 查最近的細情節，再加上較舊期間的壓縮摘要。這樣同時保有近期精度與長程脈絡，又不必無限膨脹儲存［3］。

清單 10 — 階層式摘要

def summarize_hierarchy(episodes, llm):
    by_day = group_by_date(episodes)
    daily_summaries = []
    for day, day_eps in by_day.items():
        if len(day_eps) > 5:
            summary = llm.summarize(day_eps)
            daily_summaries.append(DailySummary(
                date=day,
                summary=summary,
                episode_count=len(day_eps),
                key_outcomes=[e.outcome for e in day_eps],
            ))
            for ep in day_eps:
                ep.status = "archived"
    return daily_summaries

B. 依記憶路由

在多 Agent 系統裡，記憶可以驅動任務分派。新任務進來時，路由器查情節記憶，找出對相似任務最有經驗的 Agent。相似舊任務成功率最高者接手。這是透過記憶形成的隱性專精——專長來自累積經驗，而不是事先指定角色［6］。

清單 11 — 依記憶路由

def route_by_memory(task, agents, memory):
    best_agent = None
    best_score = 0
    for agent in agents:
        past = memory.episodic.retrieve(
            query=task.description,
            agent_id=agent.id,
            top_k=5,
        )
        success_rate = sum(
            1 for ep in past if ep.outcome == "success"
        ) / max(len(past), 1)
        if success_rate > best_score:
            best_score = success_rate
            best_agent = agent
    return best_agent or agents[0]  # 預設第一個

C. 矛盾偵測管線

語意記憶裡的矛盾是沉默殺手。Agent 先存「部署目標：staging」，後來又存「部署目標：production」，卻沒覆寫第一筆。兩筆都是 active，檢索順序不同就可能用到不同值。矛盾偵測管線定期比對同一實體—關係的所有現行事實，自動化解（留較新）或標給人審。

D. 熱／溫／冷儲存分層

不是所有記憶都需要同樣的存取速度。熱記憶（在上下文裡、即時）：當前任務狀態、現行使用者偏好、最近 3 筆相關情節。溫記憶（一次檢索、100–500ms）：最近 30 天全部情節日誌、現行語意事實、現行程序技能。冷記憶（封存、1–5 秒）：舊情節、已覆寫事實、已棄用技能。分層同時降低延遲與成本［8］。

A. 寫程式 Agent

寫程式 Agent 最受益於程序記憶。部署流程、測試指令、lint 規則、能過審查的程式模式——成功三次後就該存成技能。情節記憶捕捉除錯過程：試過什麼、什麼失敗、什麼修好。語意記憶存專案事實：哪個框架、哪個版本、哪些模式被禁。遺忘引擎讓超過 90 天的情節過期，但技能無限期保留。

B. 客服 Agent

客服 Agent 需要長期語意記憶。顧客姓名、帳號類型、過往問題、偏好溝通方式、升級歷史，必須跨數月互動持續存在。情節記憶記錄每次互動：顧客問什麼、解決了什麼、升級了什麼。與寫程式 Agent 的關鍵差異：保留期必須長得多（至少一年），遺忘引擎必須保守——刪掉顧客歷史，體驗會比留著過期資料更糟。

C. 研究 Agent

研究 Agent 需要永久語意記憶。來源、發現、假說、矛盾、論文之間的連結，會長成一份隨時間更值錢的知識圖譜。情節記憶記錄讀過哪些論文、抽出什麼、哪些搜尋查詢有用。程序記憶捕捉研究方法：怎麼搜、怎麼評、怎麼綜合。研究情境下，遺忘引擎不應讓語意事實過期——改用覆寫取代過時發現。

XV. 測試你的記憶系統

怎麼驗證記憶真的有用。

A. 失憶測試

在工作階段 1 告訴 Agent 一個事實。關掉。開工作階段 2，請它回想該事實。若不能，情節或語意記憶沒在運作。這是任何記憶系統的最低可行測試。

B. 矛盾測試

存兩筆衝突事實：「使用者偏好 Python」與「使用者偏好 TypeScript」。問 Agent 使用者偏好哪種語言。若它很有把握地答其中一個、卻不承認衝突，矛盾偵測沒在運作。正確行為：標出衝突，請使用者裁定。

C. 過期測試

存一筆 TTL 30 天的事實。等（或模擬）31 天。再問 Agent 這筆事實。若它仍在用已過期的事實，遺忘引擎沒在跑。正確行為：事實應已過期，Agent 應表示沒有當前資訊。

D. 技能晉升測試

同一任務類型成功完成三次。第四次確認 Agent 使用已存技能，而不是從頭規劃。若它重規劃，程序記憶沒被觸發。正確行為：載入技能並照步驟走，只有前置條件不滿足才偏離。

E. 負載測試

把情節記憶填到 10,000 筆，量檢索延遲。若超過 500ms，儲存需要索引，或檢索演算法需要優化。語意記憶插入 5,000 筆事實，確認衝突偵測仍在 1 秒內跑完。100 筆能跑、10,000 筆就垮的系統，還不能上線。

記憶系統測試檢查清單

  • Agent 能回想上一輪的事實（失憶測試）
  • Agent 能偵測衝突事實（矛盾測試）
  • 過期事實不被使用（過期測試）
  • 重複成功會觸發技能（晉升測試）
  • 1 萬筆時檢索低於 500ms（負載測試）
  • 遺忘引擎依排程執行（cron 測試）
  • 跨工作階段任務能保住進度（連續性測試）
  • 跨專案事實不外洩（隔離測試）

XII. 結論

模型聰明了十倍。每次工作階段結束，它還是什麼都忘。2026 年的瓶頸是記憶，不是智力。五層架構解這個問題：工作記憶管當前回合，情節記憶管發生過什麼，語意記憶管什麼為真，程序記憶管怎麼做，遺忘引擎管該刪什麼。

證據很具體：Mem0 把每次查詢從 26,000 token 降到 1,800，token 少 90%、延遲低 91%。Snowflake 加一層本體，準確率 +20%、工具呼叫 −39%。記憶第一天就能回本。

實務建議：先做情節記憶。一個會存任務結果、開工前會查的 JSON 檔。幾分鐘就能做完，立刻避免 Agent 重犯昨天的錯。再加語意記憶放耐久事實，再加程序技能放有效方法，再加遺忘引擎維持整潔。架構會複利：每一層都讓其他層更值錢。

「明天它又讀同一批十二個檔案，得到同樣的結論，再收你同一筆 token。除非你給它記憶。」
